# Matriz 0.1.0-rc.1 — notas da versão candidata

**Data:** 2026-11-19. **Estado:** versão candidata, **não publicada**: não tem tag nem release no GitHub. A tag `v0.1.0-rc.1` só é criada depois da validação final. Não é uma release de produção.

## Porquê 0.1.0-rc.1

Segue o [Semantic Versioning 2.0.0](https://semver.org/lang/pt-BR/):

- **0.x:** o MVP ainda não está completo (três dos nove incrementos estão por iniciar) e a especificação não foi validada pelo cliente. Com a versão principal 0, a API e o modelo de dados podem mudar sem garantias de compatibilidade. O contrato da API já teve uma mudança que quebra a compatibilidade (0.5.0: vários responsáveis por tarefa).
- **0.1.0:** é a primeira versão que se pode entregar: tem funcionalidades a funcionar de ponta a ponta e constrói, testa e corre de forma reproduzível com Docker Compose e CI.
- **rc.1:** é a primeira candidata. Só passa a `0.1.0` depois da validação final (Ficha 05, exercício 6) e da pipeline aprovada no GitHub.
- **Depois:** cada incremento que acrescente funcionalidades (2, 3, 7 e 8) dará uma versão menor nova (`0.2.0`, `0.3.0`, …); correções sem funcionalidades novas, uma versão de correção (`0.1.1`).

Onde está a versão:

## O que não inclui (limitações conhecidas)

- **Incremento 2 (contas e ativação):**
  - não há criação nem desativação de contas, permissão de Administrador ou links de ativação (US02, US11, US16);
  - `POST /auth/activate` está **planeada e não implementada**: o backend responde `404`;
  - o envio de emails com o Mailpit (D09) está **planeado e não implementado**: o Mailpit não está no `compose.yaml` e nenhum código envia emails;
  - as contas vêm só do seed.
- **Incremento 3:** falta a gestão da equipa do projeto (adicionar e remover membros, US04). O painel "Membros" é só de leitura.
- **Incremento 7:** faltam os pedidos de responsável (US31).
- **Incremento 8:** falta a área de administração (US12, US14, US17): troca de Gestor, lista de todos os projetos e consulta do registo administrativo. O registo guarda a criação de projetos, mas não se pode consultar.
- **Criação de projetos:** só existe na API (`POST /projects`, só o Administrador). O formulário ainda não existe.
- **Sessão:** o token não é revogado ao sair; um token copiado antes de sair continua válido até expirar (D06).
- **Âmbito:** só a execução local. O deploy continua a ser uma extensão futura (D05) e não há HTTPS.
- **Testes E2E de browser:** cobrem só um percurso (entrar, abrir um projeto e criar uma tarefa).
- **Imagem do backend:** 571 MB (registado em [verification.md §8.1](../verification.md#81-imagens-e-containers)), aceite como limitação.
- **Por verificar** ([verification.md §8.5](../verification.md#85-por-verificar)): o healthcheck do frontend na CI (o passo só espera por `/api/health`) e a forma como o diagrama Mermaid de `architecture.md` §6 aparece no GitHub.

## Como executar

```bash
cp .env.example .env               # e muda os valores; JWT_SECRET: openssl rand -hex 32
docker compose up -d --build
docker compose run --rm migrate npm run db:seed   # dados de demonstração, opcional
```

Abre `http://localhost:8080` (ou a porta de `FRONTEND_PORT`). Os detalhes estão no [README](../../README.md#execução-com-docker-compose).

## Atualizar a partir de uma instalação anterior

- **Nome do ficheiro Compose:** o `docker-compose.yml` passou a `compose.yaml`. O volume `matriz_pgdata` mantém-se, por isso os dados continuam lá.
- **`docker compose up -d`:** passa a arrancar a aplicação inteira. Para ter só o PostgreSQL no desenvolvimento local, usa `docker compose up -d postgres`.
- **`.env` da raiz:** acrescenta as variáveis novas do `.env.example` (`JWT_SECRET` e as outras). Sem `JWT_SECRET`, o PostgreSQL arranca na mesma, mas o backend não.
